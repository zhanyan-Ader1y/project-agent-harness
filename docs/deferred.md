# 这份文件是什么

**从 `DESIGN.md` 移出的设计，按"最小可用发布"分档而来。这里的每一条都是已作出的设计决定，不是废案。**

移出的理由只有一个：**它不在下面这句话里。**

> **最小可用 = 一条经验能被写进跨会话、跨成员共享的库；下一次相关提问时，它自动回到上下文里，且注入前机器验过它声称的符号真的存在。**

判据是「不做它，这句话不成立」。做了更好、但不做这句话照样成立的，移到这里。

**移走不等于削弱。** 每一节保留原文（含所有实测数字与出处）、写明为什么它不属于最小可用、写明**什么条件下把它拿回来**。拿回时应把该节原样搬回 `DESIGN.md` 对应位置。

**这份文件不常驻上下文，也不进任何 agent 的加载路径。** 它是排期文档，读它的人是决定"下一步做什么"的人。

`Intent.md` 第四节的四条不可让渡约束**没有任何一条在这里**——它们全部留在 `DESIGN.md`，由留下的部件承担：约束 4「共享的东西必须有准入」的执行者是 Review 层与 deny hook，两者都在最小可用里。

### 架构与架构决策记录（ADR）

架构分为**系统架构、代码架构、领域设计架构**。

但真正决定怎么处理的是另一条切分——**架构记录里混着三类性质不同的内容**：

| | 例子 | 过期方式 | 机制 |
| --- | --- | --- | --- |
| **规范类**（应然） | 分层、边界、命名、依赖方向 | **不因代码漂移过期**，但**会因决策被推翻而作废**——而且比描述类更隐蔽，因为不存在"代码与它不符"这个可见信号 | 被新 ADR 推翻时同步标 `supersedes` |
| **描述类**（实然） | 模块清单、依赖关系、领域划分 | 会，且无声 | 采信时以代码为准，见下 |
| **ADR** | 当初为什么这么决定 | **不会**。决策发生过就是发生过，即便后来推翻，记录本身仍准确。append-only | 无 |

**描述类的处置**：不设结构变动提醒 hook（`PostToolUse` 的 matcher 匹配的是工具名，"新增模块"不是工具名；且既然采信时以代码为准，描述陈旧本就不改变任何判断）。

约束是「**描述类架构与代码冲突时，一律以代码为准，且应就地更正描述**」——但**这条不能写在 `architecture-notes` skill 里**：危险时刻是 agent **读**架构描述并采信的那一刻，而该 skill 由 description 触发，只在**写**架构描述时加载。管住了写的人，管不住信的人。

改为一条**路径作用域规则**：

```yaml
# .claude/rules/architecture-description.md
---
paths:
  - "docs/architecture/**"
---
```

官方机制是「路径作用域规则在 Claude 读取匹配文件时才载入」——**执行者与失效点因此对齐**：读到架构描述文件的那一刻，约束自动进上下文，不依赖 agent 记得加载什么。

### 模块级知识记在哪

**不要求每个模块建 `CLAUDE.md` 与 `AGENTS.md`。** 三条理由：

**一、该记的内容比直觉少得多。** `/doctor` 的 trim 规则给了现成判据（<https://code.claude.com/docs/en/memory>，2026-09-02 读）——删掉**能从代码推导的**（目录结构、依赖清单、架构概览），保留**坑、rationale、与工具默认不同的约定**。

「记录模块细节」这个目标本身要收窄：细节大多可从代码推导，写下来就是**制造第二事实源**，正撞目标四。

**二、`AGENTS.md` Claude Code 不读**（"Claude Code reads `CLAUDE.md`, not `AGENTS.md`"，同上出处）。仅当团队确实在用别的 agent 工具时才需要，做法是 `@AGENTS.md` 导入或符号链接——一份内容两个工具读，不并存。注意**导入的文件是启动时加载的**，会抵消按需加载的好处。

*该行为可能随版本变化，本节结论依赖它，须随官方文档复核。*

**三、嵌套 `CLAUDE.md` 成本低但形态不对。** 官方明确子目录下的 `CLAUDE.md` 按需加载，所以常驻成本的担心不成立。但对"只影响一部分代码库"的内容，官方建议 **skill 或 path-scoped rule**：

| | 嵌套 `CLAUDE.md` | `.claude/rules/` + `paths:` |
| --- | --- | --- |
| 按需加载 | ✅ | ✅ |
| 集中可审 | ❌ 散落各模块 | ✅ 一处看全 |
| 边界 | 只能按目录 | 可跨目录，模块边界与目录不一致时仍管用 |
| 冲突 | 多份互相矛盾（官方点名的问题） | 一处可查 |

**分流规则**（属 `architecture-notes` 管辖）：模块级的坑与约定 → `.claude/rules/<module>.md` + `paths:`；多步流程 → skill；**能从代码推导的 → 不写**。

| 信号 | 挂在 |
| --- | --- |
| 一次 hook deny 或权限拒绝（**须排除本项目自己的闸门**，否则"我写记录被拒了"会自我指涉地构成一条经验） | `PostToolUse` |

| 产生了工作区之外的动作 | `PostToolUse` |

**第四条不可省**：它是乙分支里最强的信号（TRACE 的 142 条数据全部由此挖出），但它不是工具事件——**用户在对话里做出的纠正，前三条一条也观测不到**。若缺它，这条信号就只在 agent 恰好主动加载 skill 时才用得上，而设立触发机制的全部理由正是不依赖主动加载。

| --- | --- | --- | --- |
| `PostToolUse` / `Stop` | 三条可观测信号 | 唤起 `experience-intake` | **库长期为空且无人知晓** |

`UserPromptSubmit` 行的第二项作用（其第一项检索留在 `DESIGN.md`）：

> ② 判定本轮提示是否构成一次纠正，命中则唤起 `experience-intake`｜失效后果：用户纠正无人观测

## 为什么不在最小可用里

**"能写进去"与"一定会写进去"是两件事，最小可用只要求前者。** 用户踩到坑、说一句"把这个记下来"，agent 按 description 加载 `experience-intake`，走写入脚本入库——这条路径在没有触发 hook 时完整成立，最小可用那句话因此成立。

触发 hook 解决的是**覆盖率**问题：不靠人记得说那句话。这是真实收益，但它是对一条已经跑通的路径的加固，不是那条路径本身。

**风险如实记下**：`DESIGN.md` 给这条 hook 的失效后果是「**库长期为空且无人知晓**」。推后它就是接受这个后果一段时间——所以下面的拿回条件写成了可观测的量，而不是"看着办"。

## 什么条件下拿回来

**第四条信号（`UserPromptSubmit` 上的纠正判定）应当第一个拿回**，理由在原文里：检索 hook 已经因最小可用而存在，纠正判定挂在同一处，**不增加 hook 数量**，成本接近于零，而它是乙分支里最强的信号。

具体条件：

- **拿回第四条**：最小可用的检索 hook 一落地，就可以在同一个脚本里加判定。**不必等任何观测数据。**
- **拿回前三条（`PostToolUse`）**：写入路径跑通后，**库里的条目数明显低于同期实际发生的纠正与失败次数**——这就是"该记的没记"的可观测形态。若没有这个落差，前三条的收益是假设的。

拿回前三条时须带上原文的两个约束：hook deny 信号**必须排除本项目自己的闸门**（否则自我指涉）；`Stop` 与 `PostToolUse` 的选择要复核，别把一条信号挂成两次唤起。

# Dedup 层：否决式规则，默认回退新建

**当前状态：0 行代码。判据文件 `skills/experience-intake/dedup.md` 未建。**

## 移出的原文

**语义相似不等于经验等价。经验的边界在于适用场景的约束条件。**

以下任一成立即**不得合并**：

- **When 不同不能合**——即使结论看起来相似，场景不同就是两条
- **主结论类型不同不能合**——操作建议 / 风险规避 / 排查方法不能混为一谈
- **局部子机制与完整系统经验不能合**——粒度不一致，不能互相替代
- **同一技术事实但用途不同不能合**
- **★ 禁止桥接式合并**——A 与 B 有重叠、B 与 C 相关，**不能据此推断 A 与 C 重复**

> 一旦桥接式合并把边界不同的经验串联归并，**边界信息就永久丢失了**。

# Merge 层：`update` / `skip` / `contradict` 与唯一目标判定

**当前状态：这三个动作 0 行代码。** `skills/experience-intake/merge.md` **已建**（2026-09-04），但它只承载甲/乙分支——**本节这三个动作在那份文件里一句都没有**，也不该有：写它们等于让模型判"该不该合并"，而合并的判据在脚本里。

**注意本节只移出三个动作与唯一目标判定。** `create` 与甲分支的晋级逻辑（查库 → `occurrences + 1` → `candidate` 翻 `confirmed`）**留在 `DESIGN.md`**，因为它决定"什么进入检索"，不留就没有经验能被取回来，最小可用那句话不成立。

## 移出的原文

四种动作（`create` 一行留在 `DESIGN.md`）：

| 动作 | 何时 |
| --- | --- |
| `update` | 与历史同向，且带实质新信息 |
| `skip` | 核心结论可互相替代 |
| **`contradict`** | **核心结论直接冲突——标记，不自动取舍** |

- **唯一目标判定前置**：先召回相关子集，判断是否存在"唯一最合适的目标"。**没有就默认回退 `create`**——避免把一条不够匹配的历史经验硬推成 update 目标而污染边界。
- **`update` 必须自检**：合并后 When 是否过度泛化（丢了场景约束）、What 是否保留了最具体最可执行的建议、Why 是否保留核心机制、是否引入了原经验不支持的新结论。参照数据：他们的 update **Recall 96.30% 但 Precision 仅 78.79%——模型有明显的"积极合并"倾向**，这是最需要防的一类。
- **`contradict` 不自动放过，也不自动决断**：新旧认知不一致**本身就是有价值的信号**，不应被自动压制。标记后进人工裁决队列。

**`contradict` 是唯一进人工的路径**，且它不是准入审批——它处理的是两条已入库经验的冲突，不改变"skill 是准入唯一裁决者"。

条目结构里的对应字段（字段本身**保留在 `DESIGN.md` 的 schema 中不动**，此处只记它的产生机制被推后）：

```text
  contradicts       走 contradict 时：与之冲突的 memory_id
```

`status` 枚举里的 `contradicted` 同理——枚举留在 schema，写它的路径推后。

## 为什么不在最小可用里

**这三个动作全部需要"库里已有相关条目"作为输入。** 一个空库里，`update` 找不到更新目标，`skip` 找不到可替代的结论，`contradict` 找不到冲突对象。它们不是被削弱了，是**触发条件尚未出现**。

关键是：**推后它们不改变任何行为，因为原设计自带的默认路径就是 `create`。** 原文写着「没有就默认回退 `create`」——推后 `update`/`skip` 等于让这条默认路径成为唯一路径，走的仍是设计规定的分支，不是新行为。

`contradict` 值得单独说一句：它是**唯一进人工的路径**，也是三层里唯一会产生人工队列的部件。在库里只有个位数条目时建一条人工队列，队列本身比它处理的冲突更重。

## 什么条件下拿回来

**分两批，条件不同：**

1. **`update` / `skip` / 唯一目标判定**：库里出现第一次「新候选与某条已入库经验指向同一目标」的实例。在此之前，全部走 `create` 是设计规定的正确行为，不是缺陷。拿回时**必须同时拿回 `update` 自检的四问**——参照数据 Precision 78.79%、"积极合并"倾向，是这一层最需要防的一类，没有自检就是把那个 21% 直接放进库。

2. **`contradict` 与人工裁决队列**：出现**第一对结论直接冲突的已入库条目**。这是一个可以等到它自己发生的条件——冲突发生时，被冲突的两条经验都会被检索出来注入同一个上下文，很难不被注意到。

**两批都不该早于库里有两位数条目。**

# 淘汰、库审计与 `expiration_date`

**当前状态：0 行代码。`assert-replay` 里没有库审计入口。**

## 移出的原文

### 淘汰：挂在定期库审计上

*（原文标题写"三条判据"而表格只列两条，是原文自带的不一致。第三条应为"`confirmed` 但超期未校验则强制重校验"，在「判定结果不回写」那次删掉了却没改标题。此处按两条记。）*

腾讯团队把这条列为三个未解方向之一：**长期未命中、未采纳的经验没有自动淘汰机制，库会随时间静默膨胀**；项目演进时（模块重构、能力下线）历史经验可能**集体失效**，且没有识别"需要复核"的能力。

> 生产决定基线 → 使用暴露问题 → 维护反哺生产。**任一环不闭合，经验系统就会从资产退回为噪声。**

**本项目的失效范围比他们更大**——经验存云端、跨仓库共享，一次模块重构可能让另一个仓库里的召回集体失准。

淘汰不新增组件，挂在 `scripts/assert-replay` 的**库审计**上。但因为判定结果不回写（见 `DESIGN.md`「判定结果不回写共享库」），它**不能是自动的**：

**人工触发的离线审计** —— 跑一遍库，产出一份报告给人看；**撤回是人的决定**，写 `retracted` 是人的动作。

| 报告里列什么 | 依据 |
| --- | --- |
| `verdict: fail` 且 `verified: true` 的条目 | `evidence_cmd` 跑不通，或 `files`/`symbols` 已不存在 |
| `recalled_n ≥ 10` 且 `adopted_n = 0` 的条目 | 召回了从不被采纳，等同噪声 |

**`verified: false` 的条目不进报告**——那是"查不动"（工具不可用、条目属于别的仓库），不是"断言为假"。两者合流的话，一台没装 `rg` 也没装 `grep` 的机器跑一次审计，会把全库带 `symbols` 的条目一并列为待撤回。

第二条依赖采纳计数，而采纳计数依赖那个尚未解决的观测问题。

**为什么不能自动**：自动淘汰 = 把 pass/fail 写回共享库 = 那条出向信道。人在回路里，判定就不再是命令退出码的确定性函数，问答节奏也不由攻击者掌握。**代价是淘汰不再实时**，库的膨胀速度取决于人多久跑一次审计。

### `expiration_date`：一条不碰出向信道的自然退场

mem0 的 `add` 支持 `expiration_date`（实测原样保留），到期后条目默认不再被检索到（`search` 的 `show_expired` 默认 false）。

**它是写入时定的，不是判定的函数**——因此完全绕开上面那条信道，却仍然让库不会无限膨胀。

它**不能**取代基于失效的淘汰：它不知道代码变了。两者分工——

| | 管什么 |
| --- | --- |
| `expiration_date` | **没人再用的老经验自然退场**，自动、无需回写 |
| 人工离线审计 | **已经失效的经验**（命令跑不通、符号没了），由人撤回 |

### `assert-replay` 的两个延后消费方

`DESIGN.md`「目标四的执行者」一节列了四个消费方，其中两个随本节推后：

- **定期审计 mem0 库**
- **淘汰判定**

留在最小可用里的两个是**写入前自检**（`--mode full`，作者自己机器上跑自己写的命令）与**注入前校验**（`--mode symbols`，不执行任何命令）。

`assert-replay` 的实现（`plugins/experience/scripts/assert-replay.js`，898 行）与它的回归用例**全部留在仓库里**，包括 `--mode full` 那一半与五道执行边界——推后的是**两个调用点**，不是代码。

条目结构里的三个字段——`recalled_n`、`adopted_n`、`expiration_date`——**定义在 `DESIGN.md` 的「条目结构」一节，不在这里复述**；此处只记它们的**消费方**被推后，字段本身留在 schema 中不动。

（不复述是有意的：字符级重叠扫描把原先此处的一份 schema 拷贝标为 91 字符连续重合。schema 改动时两处都要跟着改，正是前身清单第 5 条「插入新内容必须删除被它取代的旧内容」的高发形态。）

## 为什么不在最小可用里

**淘汰的对象是"库随时间静默膨胀"和"历史经验集体失效"。一个还没写进过一条经验的库，两者都不存在。**

这是本次分档里最没有争议的一项：它按定义就是"已经跑了一段时间之后"的维护动作。原文引的那句「生产决定基线 → 使用暴露问题 → 维护反哺生产」自己就写明了顺序——维护是第三环。

还有一条更硬的：**淘汰的第二条判据（`recalled_n ≥ 10` 且 `adopted_n = 0`）依赖一个无人解决的观测手段。** `DESIGN.md` 如实记着「这个观测手段目前无人解决，本项目也没有方案」，腾讯团队也没解决。这条判据现在写不出来。

`expiration_date` 是唯一一个"现在就能做且几乎零成本"的部分（写入时填一个日期字段），但**它的存在理由是"让库不会无限膨胀"，而库现在是空的**。它随本节一起推后，是为了让淘汰这件事作为一个整体被重新审视，而不是先落一个半截。

## 什么条件下拿回来

**按三个条件分批：**

1. **`expiration_date`（最先）**：库里条目数达到**注入双上限开始频繁截断**——即一次检索命中数经常超过 5 条 / 1,500 tokens，说明库已经在膨胀。它是写入时的一个字段，改写入脚本即可，不需要审计入口。
2. **人工离线审计的第一条判据（`evidence_cmd` 跑不通 / `files`·`symbols` 已不存在）**：出现**第一条实际失效的条目**——最可能的触发是一次模块重构后，某条经验里的符号没了。这需要在 `assert-replay` 上开库审计入口 + `--mode full`，代码基础已经在仓库里。
3. **第二条判据（召回 ≥10 次、采纳 0 次）**：**`adopted_n` 的观测手段有解之后**。这是一个已登记的未解缺口（`docs/review/2026-09-02-design-review-tracking.md` 亦有记录），不该为了凑齐判据而勉强做。

**三条都不该早于最小可用发布后的第一次真实使用周期。**
