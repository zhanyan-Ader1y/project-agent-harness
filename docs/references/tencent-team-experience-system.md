## 零、一句话概括他们的路

> 初版：上报所有对话 → 让 AI 提取"你认为有价值的内容" → 入库。
> 结果：**约 90% 是废经验。**
> 最终：对话上报 → 主题分组 → 经验抽取 → **Review → Dedup → Merge** → 入库 → 召回统计。
> 垃圾率 90% → **5%**，最终入库率约 80%。

## 一、直接挑战本项目当前设计（最重要）

### 1.1 「让 AI 自己判断自己产出经验的价值 = 裁判兼运动员」★★★

原文逐字：

> **让 AI 自己判断自己产出经验的价值，等于让裁判同时当运动员——在工程上无效。**

**本项目当前设计正是这个形状**：`DESIGN.md` 定「`experience-intake` skill 是准入的唯一裁决者」，而候选经验也由同一个 agent 在同一个会话里产出。

这与前身 Themis 那条实测（`实现者不得验证自身产出`，11 次失效 10 次）是**同一个结构问题的两次独立观察**。

**他们的解法不是加人工审批**（这一点重要，不违反已定决策）：而是把治理拆成**三个独立的 prompt / 模型**，各自只做一件事，在候选经验入库前逐层过滤。裁决者与产出者因此不是同一个上下文。

### 1.2 我们的准入判据（重复 / 高代价）可能选错了维度 ★★★

他们对"什么算经验"的判定标准只有一条：

> **被召回后，Agent 能否产生正向的行为变更。**

由此推出的分类不按主题、不按重要性，而按**认知障碍**——即"Agent 能不能自己发现"，理由是这个维度**客观可判定**：

| 镜头 | 障碍本质 | 例 |
| --- | --- | --- |
| **黑话镜头** | 语义不可发现 | 项目内"D 站"指盗版站点——AI 只看到字母 |
| **索引镜头** | 位置不可发现 | "直达页面功能在 xhome 模块，关键类 FastCutXXX"——读代码找不到，要知道"去哪找" |
| **逻辑镜头** | 行为不可发现 | "stop hook 不能同步上报"——AI 常规推理认为上报是轻量操作，推不出并发阻塞风险 |

> 其中最关键的是 **"不容易直接发现"——如果 Agent 自己就能推出来，召回它没有任何额外价值。**

**对本项目的含义**：`DESIGN.md` 的甲（重复出现）/ 乙（单次高代价）量的是**频次与严重度**，不是**可发现性**。一个高频且昂贵、但 Agent 自己就能推出来的错误，按我们的判据会入库，按他们的判据零价值。

**而本项目在别处已经写了同一条原则**——「能从代码推导的 → 不写」。三镜头是它更锋利、更可操作的表述，应当上升为准入判据的第一道，甲/乙退为第二道。

### 1.3 他们点名说 mem0 的前提假设在编程场景不成立

> Mem0 是一套 Agent 长期记忆基础设施。ADD/UPDATE/DELETE/NONE 四类判定、混合检索，生命周期管理完整。**但整个设计的假设是"记忆大体有价值"——这个假设在编程场景的高噪声对话里完全站不住。**

**这不构成推翻云端 mem0 的理由**（存储选型是已定决策），但它精确指出了后果：**mem0 不会替你做质量治理，治理必须在写入它之前全部完成。**

本项目的 `scripts/experience-write` 正是这个位置——**但它当前只做「查库 → 交 skill 判定 → 红线过滤 → 写入」，没有 Review / Dedup / Merge 三层。**

### 1.4 各层的默认方向必须不同，本项目只有一个闸门一个默认

> Review **默认保留**（误杀一条高价值经验的代价大于放行两条垃圾）、Dedup **宁严勿宽**（误合并的边界污染不可逆）、Merge **保护历史边界**（已有经验是已验证资产，新经验要跨过更高门槛才能修改它）。**"宁可错杀"和"宁可放过"的方向在各层完全不同。**

本项目当前只有一道准入闸门，没有区分"漏记"与"误记"哪个代价更高，也没有为"修改已有经验"设置更高门槛。

### 1.5 纯文本审核挡不住编造的技术事实——他们的解法与本项目的 `assert-replay` 同源

真实案例：系统抽出一条经验，称对接 `FastScrollBar` 应使用 `attachToQBListView()`。**有场景、有方法名、有操作指引，纯文本 Review 大概率放行。** 他们做了**源码定向搜索**，发现该类只有 `attachToRecyclerView()` 与 `attach()`，`attachToQBListView()` 根本不存在（正确的是 `FastScrollBarCompat.attachToQBRecyclerView()`）。判为事实性错误，拦截。

失败模式的描述值得逐字记住：

> 如果这条经验入库，Agent 会按指示调用一个不存在的方法，编译失败。**更麻烦的是 Agent 会怀疑自己理解有误，而不是怀疑经验有问题——陷入反复重试的恶性循环。**

**这是本项目 `scripts/assert-replay` 存在理由的独立佐证**，并把它的适用面扩大了一类：不只重跑 `evidence_cmd`，还应校验经验里提到的**符号是否真的存在于代码库**。

## 二、可直接抄的

### 2.1 九类垃圾特征（可直接作为 `experience-intake` 的排除清单）

| 特征 | 说明 |
| --- | --- |
| 事实性错误 | 编造不存在的约束，把对话里的临时说法当规则 |
| 通用常识 | 任何项目都适用，不体现团队特异性 |
| 对话摘要 | 只复述过程，没有沉淀成可复用判断 |
| 一次性 case | 只对当前任务有效，不能迁移 |
| 用户主观偏好 | 个人选择，不代表团队规范 |
| 缺少上下文 | 不知道对应哪个模块/组件/接口 |
| 粒度混用 | 一条里兼顾通用规则和 case 特定信息 |
| 不可执行 | 只有抽象建议，Agent 看完不知道怎么做 |
| 证据不足 | 对话里没有足够依据，模型自己推断过多 |

方法论：**先研究垃圾，再反推好经验**——"好经验"难一次定义到位，"垃圾"的特征更容易归纳。

### 2.2 可审计输出：要求模型为每条经验给出三个维度的解释

- 为什么这是经验（解决了什么可复用问题、是否项目特有）
- 命中了 prompt 中的哪些排除规则（通过了哪些垃圾检查）
- **对话证据是什么（哪几轮对话支撑）**

> 这让模型的判断过程脱离黑盒，也为后续 prompt 迭代提供了错例定位的依据。

**与本项目的 `high_cost_anchor` 同源**，但覆盖面更广——每条经验都要自证，不只走乙分支的那些。

### 2.3 Dedup 的禁止合并规则（直接适用于本项目的「同型判定」）

- **When 不同不能合**——即使结论相似，场景不同就是两条
- **主结论类型不同不能合**——操作建议 / 风险规避 / 排查方法不能混为一谈
- **局部子机制与完整系统经验不能合**——粒度不一致
- **同一技术事实但用途不同不能合**
- **★ 禁止桥接式合并**——A 与 B 有重叠、B 与 C 相关，不能据此推断 A 与 C 重复

> **经验的边界在于适用场景的约束条件，语义相似不等于经验等价**——一旦桥接式合并把边界不同的经验串联归并，**边界信息就永久丢失了**。

**本项目当前的同型判定是「语义相似度 ≥ 0.85 且至少一个结构锚重合」——正是他们警告的那种做法。** 结构锚重合恰恰可能成为桥接的桥。

### 2.4 Merge 的四种动作与三条主线

四种动作：`create` / `update` / `skip` / **`contradict`**（核心结论直接冲突 → 标记冲突、提人工裁决）。

- **唯一目标判定前置**：先召回相关子集，判断是否存在"唯一最合适的目标"。没有就**默认回退到 create**——从根本上避免"强行匹配"污染边界。
- **Update 必须自检**（`quality_check`）：合并后 When 是否过度泛化、What 是否保留了最具体最可执行的建议、Why 是否保留核心机制、是否引入了原始经验不支持的新结论。
- **Contradict 不自动放过，不自动决断**：冲突意味着团队新旧认知不一致，**这本身就是有价值的信号**，系统只标记，决策走人工。

**`contradict` 这一类本项目完全没有。** 当前只有 candidate / confirmed / retracted，没有"两条经验互相矛盾"的表示。

### 2.5 Prompt 迭代的固定流程与三个指标

> 固定对话样本 → 当前 prompt 提取 → 与人工标注对齐 → 分析错例 → 修改 prompt → 重新评测 → 对比指标变化

三个指标**必须一起看**：**Recall**（该提的提了多少）、**Precision**（提的有多少不是垃圾）、**Garbage Rate**（不该提的提了多少）。

> 不能只看一个——**只看 Precision 模型会过度保守，只看 Recall 垃圾会变多。**

### 2.6 一个反直觉的对照实验

主题分组时，一组给分组片段附上 session 上下文大纲，一组不给。

> **带大纲的那组产出了更多垃圾**——因为大纲引导模型做泛化推断，反而偏离了分组片段里实际发生的具体经验。分组本身的粒度就够了。

**给模型更多上下文不一定更好。** 这对本项目的检索注入同样成立：注入更多经验未必带来更好行为。

## 三、实测数字（本项目没有任何同类数据，这是唯一可参照的基线）

**规模**：6 个仓库、50+ 研发、1,236 次独立对话 → 1,022 条候选 → **789 条入库**，Pipeline 稳定运行 30+ 次。

**质量**：垃圾率 90% → **约 5%**；最终入库率约 **80%**。

**Dedup**（260 条经验、4 个分组）：整体 F1 **71.79%**；严格重复（What 与 When 均相同）Recall **91.67%**。
漏判集中在 What 包含/相交、When 不同/相交的边界模糊组合——策略更倾向保护差异。
**batch 间波动明显**：batch_004 的 6 个人工正例只识别出 1 个。**说明 prompt 对边界的敏感度在输入分布变化时仍不稳定。**

**Merge**（六轮实验、157 个样本）：整体 F1 **94.27%**；Create F1 **96.46%**（最稳）；Skip Precision **100%** 但 Recall 85.71%；
**Update 是最大问题：Recall 96.30%，Precision 仅 78.79%——模型有明显的"积极合并"倾向**，把本该 create 的判成了 update。

**召回**（最新 125 次真实检索）：请求级召回率 **68.8%**，no_hit 仅 **4.8%**，**平均每次注入 2.4 条**，平均耗时 **1,299 ms**。

> 「平均注入 2.4 条」与本项目 `DESIGN.md` 定的「每轮 ≤ 5 条」量级一致，可作为该上限的旁证。

**架构**：他们没有自建检索——经验写入 IWIKI，Knot 知识库自动索引，**Agent 经 MCP 协议检索并注入**，另有上报旁路实时记录召回率。**与本项目「MCP 检索 + 脚本写入」的形态一致。**

## 四、他们没解决的三件事（本项目会撞上同样的）

原文结语列的三个方向，**本项目当前一件也没有对策**：

1. **经验质量**：事实性错误仍难以纯文本识别，源码探索只覆盖部分场景；三镜头之外的边界类型未充分识别；评测集规模有限，prompt 迭代边际收益在收窄。
2. **使用效率**：**命中不等于采纳——目前缺乏观测 Agent 是否真的依据经验改变行为的手段**；召回侧唯一目标判定偏粗，容易"召回了但用不上"。
3. **管理维护 ★**：**长期未命中、未采纳的经验没有自动淘汰机制，库会随时间静默膨胀**；项目演进时（模块重构、能力下线）历史经验可能集体失效，**没有自动识别"需要复核"的能力**。

> 三者构成闭环：生产决定基线 → 使用暴露问题 → 维护反哺生产。**任一环不闭合，经验系统就会从资产退回为噪声。**

**第 3 条对本项目尤其致命**：`DESIGN.md` 有 `retracted` 状态但**没有淘汰机制**，也没有"项目演进导致经验集体失效"的复核路径。而本项目把经验存在云端、跨仓库共享，**失效范围比他们更大**。

## 五、四条方法论（原文第八节）

1. **先定义资产边界，再做自动化沉淀。** 不定义"什么算经验"就直接自动提取，系统会把对话摘要、通用建议、一次性 case 全塞进库。**关键不是"多提取"，而是"高置信地沉淀"。**
2. **分层治理，别用一个 prompt 解决所有问题。** 各层目标不同、指标不同、prompt 设计不同；揉在一起各层目标会互相牵制。**多个针对性模型各做一件事，比一个通用大模型一次搞定更可靠。**
3. **默认策略按业务风险分别设计，没有统一答案。**（见 1.4）
4. **Prompt 优化要从错例中抽象规则，不是凭感觉改。** 固定评测集防止数据泄露和过拟合。**整个链路是工程化的，不是手艺活。**

## 六、逐字保留

> 让 AI 自己判断自己产出经验的价值，等于让裁判同时当运动员——在工程上无效。

> 过程录像不等于经验。自动提取放大候选集的同时，也在同步放大噪声。**不加过滤的自动提取，就是一个垃圾放大器。**

> 判定一条信息是不是经验的标准只有一个：**被召回后，Agent 能否产生正向的行为变更。**

> 如果 Agent 自己就能推出来，召回它没有任何额外价值。

> 经验的边界在于适用场景的约束条件，语义相似不等于经验等价。

> 更麻烦的是 Agent 会怀疑自己理解有误，而不是怀疑经验有问题——陷入反复重试的恶性循环。

> 任一环不闭合，经验系统就会从资产退回为噪声。

> 经验系统的本质不是技术系统，是**团队认知能力的工程化管道**。

## 七、落到本项目的行动项

**八条已于 2026-09-02 全部采纳，落点见 `DESIGN.md`。** 本节保留原始出处与理由，便于回溯。

| # | 落在 `DESIGN.md` 何处 |
| --- | --- |
| 1 三镜头提为第一道判据 | 抽取判据 → 第一道：可发现性 |
| 2 拆成独立判定 | 写入路径：脚本编排三次独立判定 |
| 3 九类垃圾特征 | Review 层 |
| 4 同型判定改否决式 | Dedup 层（旧的 0.85 相似度规则已废弃） |
| 5 补 `contradict` | Merge 层 + 条目结构 `status` |
| 6 补淘汰机制 | 淘汰：不设淘汰，库必然静默膨胀 |
| 7 `assert-replay` 扩符号校验 | 目标四的执行者：断言重跑器 |
| 8 三指标一起看 | 约束 → eval 套件 |

原始条目：

1. **把「三镜头」（可发现性）提为准入的第一道判据**，现有甲/乙（频次/严重度）退为第二道。理由：一个 Agent 自己就能推出来的经验，无论多高频多昂贵，召回价值为零。这与 `DESIGN.md` 已有的「能从代码推导的 → 不写」同源，只是更可操作。
2. **`experience-intake` 不能既产出又裁决。** 不加人工审批的前提下，把治理拆成写入脚本内的**两到三次独立判定**（各自独立上下文、各自的排除清单），而非一个 skill 一次判完。
3. **九类垃圾特征直接作为排除清单写进 `experience-intake`。** 零成本，且是他们把垃圾率从 90% 打到 5% 的起点。
4. **同型判定改写**：当前「语义相似 ≥ 0.85 且结构锚重合」正落在他们警告的桥接式合并上。改用**否决式规则**（When 不同不能合、主结论类型不同不能合、粒度不同不能合），并**默认回退到新建**。
5. **补 `contradict` 状态**：新旧经验核心结论冲突时标记而非自动取舍——冲突本身是信号。
6. **补淘汰机制**：长期未命中 / 未采纳的经验需要自动降级或复核，否则库会静默膨胀。本项目跨仓库共享，失效范围比他们大。
7. **`assert-replay` 扩一类**：除重跑 `evidence_cmd`，还应校验经验中提到的符号是否真的存在于代码库（他们的 `FastScrollBar` 案例）。
8. **评测指标改为三个一起看**：Recall / Precision / Garbage Rate。只看其一必然跑偏。
