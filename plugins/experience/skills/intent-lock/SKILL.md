# intent-lock

把刚谈定的意图，收成一份**下游能拿来比对**的文件。

## 它和 brainstorming 产出的设计有什么不同

`brainstorming` 已经产出了意图与方案，写得比这份细得多。**这份的全部增量在"可比对"三个字上。**

一份散文式的设计稿，下游没法拿它问"这次改动偏离了吗"——因为读它的人（或机器）得先自己归纳出判据。意图锚就是**把那个归纳提前做掉一次**，写成固定的几节。

**所以它必须短。** 长了就退化成设计稿的副本，而副本会和正本漂移——那正是目标四要防的第二事实源。

## 写在哪

仓库根的 **`Intent.md`**。一个仓库一份，记当前在做的这件事。

**不放进 `docs/`**：它要被每次提交时读到，放在根目录是为了让人和机器都不必去找。

## 五节，一节都不能少

**可以多，不能少。** 下游按**小节标题**定位（不按序号），所以多加一节、或用「四、明确不做的」这种带序号的写法，都不影响。

```markdown
# 设计意图

## 一、要解决的问题
一到三句。**用问题的语言，不用方案的语言**——写"每次进项目都从零开始"，
不写"要做一个记忆系统"。方案会变，问题不会。

## 二、目标
原始表述，**逐字保留提出时的措辞，不要改写成更专业的说法**。
改写会悄悄改变范围，而且改完就再也追不回原意了。

## 三、不可让渡的约束
存在理由层面的。判据：**违反其中任何一条，这件事就没有必要做了。**
写不出这种分量的，属于第四节而不是这里。

## 四、明确不做的
**这一节是本文件里最值钱的。** 列在这里是为了让偏离可判——
哪天做了其中一项，那是**意图变更**，不是实现细节。

尽量写成能机械比对的形态：不引入某个依赖、不新建某个目录、
不碰某一类文件。写不成机械形态的就照实写成一句话，也留着。

## 五、怎样算偏离
三到五问，每一问都要能用"是/否"回答。答不上就是偏离。
```

## 三条硬要求

**第二节逐字保留。** 提出目标的人用的措辞里带着范围，你改写一次，范围就动一次，而且没人会发现——因为改写后的版本读起来往往更"专业"。

**第四节要能被检查。** "不做过度设计"没法比对；"不引入新的运行时依赖，即不出现 `package.json`"能。两者都可以留，但至少要有几条是后者——**没有可机械比对的条目，下游的检查就只剩一句空提醒。**

**选锚只有一条判据：它出现在改动清单里，就意味着出问题了。**

| 好锚 | 坏锚 |
| --- | --- |
| `package.json`、`node_modules`（本项目零依赖，出现即意图变更） | `src/`、`evals/`（每次提交都命中） |
| `.themis/`（前身那套控制面，永远不该出现在这里） | `test`（太短，命中一切） |

**一个每次提交都命中的锚，会把提醒变成噪音，人于是学会整段跳过——那比没有锚更糟。** 加完锚拿全仓文件清单试一遍：一次都不该命中。

**第五节的每一问都要能答"否"。** 一个永远答"是"的问题不是判据。自检方式：想一个具体的、明显跑偏的改动，逐问过一遍——如果它全部答"是"，这几问就是摆设。

## 写完之后

**它会在每次 `git commit` 时被读到**（`hooks/intent-drift.js`），连同本次改动的文件清单一起摆到面前。那一刻要回答的就是第五节那几问。

**这是提醒，不是拦截**——不会挡住任何提交。它解决的是"忘了对照"，不是"不许偏离"。

## 什么时候改这份文件

**意图真的变了的时候，而且要明说。** 

发现改动与锚冲突时，有两条路，**选哪条要说出来**：

| | 什么时候 |
| --- | --- |
| 改回去 | 这次改动确实跑偏了 |
| 改锚 | 意图本身变了——**那是一次决定，要有人拍板，不是顺手改掉** |

**最坏的做法是悄悄改锚让它对上这次改动。** 那等于把判据改成结论，此后这份文件再也判不出任何东西。
